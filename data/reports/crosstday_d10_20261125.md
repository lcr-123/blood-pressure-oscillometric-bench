## 2 Windows 重启与写通道死亡：只有物理拔插能救

### 2.1 现象

- `(Get-CimInstance Win32_OperatingSystem).LastBootUpTime` → **2026-11-25 12:08:35**。
- 编排日志 `tmp/omniprobe/crosstday_d10_run.log` 的 mtime 停在 **12:02:43**，最后一行是
  块B 第 1 轮 `capture … -115928 gate=USABLE slope=-1.75`；**没有** `capture(s) kept` 行。
- manifest 里**没有** day 10（编排只在 `finally` 里写 manifest，见
  `tmp/run_crosstday_20261116.py:365-370`），这也让重跑可以继续用 `--day 10` 而不触发
  `:282-284` 的防覆写 `SystemExit`。
- 被中断的那一刻在 `data/raw` 留下一个**孤儿 ndjson**
  `standard120_080_target275_peakwindow_20261125-120244.ndjson`（**2,882,808 B**）：9366 行、
  3621 个样本、末样本 `est=2.4 raw=1570 sensor=271`，**没有 `[Boot]`、没有 `reset_csr`**，
  最后一行仍在正常打印 `[Pressure]`（`i=2447 t=4598860`）——即**主机侧进程被 OS 直接切断**，
  不是 MCU 复位、也不是串口出错。

### 2.2 重启之后的怪状态：读得动、写不动

| 方向 | 结果 |
|---|---|
| 读 | 直连 `serial.Serial('COM6', 115200)` 3 s 读到 4154 B `[Pressure]`，`est` 稳在 −0.1…+0.4 mmHg（泵停、阀开、袖带通气），20 s 只读窗口里 **`state-changing text lines: 0`** |
| 写 | 一律失败：OmniProbe 桥回 `{"ok": false, "error": "Failed to write to serial port: 信号灯超时时间已到 (os error 121)"}`；直连 pyserial 抛 `Write timeout`（`write_timeout=3.0`）；`micu-omniprobe-ai` 技能自带的 `client.py write` 回 `错误: timed out` |

`os error 121`（ERROR_SEM_TIMEOUT，即"信号灯超时"）出现在 USB-CDC 的 **OUT 端点**上，而
IN 端点照常收数据 —— 这是 Windows 重启后 USB 管道一半卡死的典型形态，和 OmniProbe 的
进程状态无关。

   started after hold` 与 `[Deflate] done; valve2 closed` 之间只有压力行。要定位得在
   `main.c` 的 PWM 节流环路里加打印（占空比、每步目标、实际压差），**批次期间不能改**。
   这一条已升为本批次最值得追的固件问题。
2. **写通道 `os error 121` 的判据要不要写进接线/操作文档**。今天证明了"读通写不通 → 只能
   物理拔插"，而且非管理员会话连 PnP 复位都做不了。建议在方案的"每天开机检查"里加一条：
   先发一条 `status` 确认写通道，再看压力流。
3. **文本时间戳是批处理的**（§3.2），同批多行共用一个 `timestamp` 毫秒值。这会让"到压→超压
   相距多少毫秒"这类测量退化成"相距几行"。要么在采集脚本里把批次边界也记下来，要么在
   报告里统一改用"行距 + 25 ms 采样格"表述。
4. **`[Capture] duration` 与 `(n−1)×25` 的口径**已核对一致（D9 44 条、D10 15 条），但
   `[Capture] n=` 在同一份 ndjson 里会出现多条（`status` 回显上一轮残留值），必须用该轮
   export 的 `begin.n` 去匹配。这一点应该写进 `tools/` 的说明里，而不是靠每个分析脚本自己记得。
5. **P4（`SIM_STD255_195`）为什么系统性更陡**：D5 −3.34/−3.34/−3.40、D8 −2.71、D9 −2.42、
   D10 −2.90，十一天里 11 次是本日最陡。袖带体积分段表（0.55 cc）与其它档差距不大，
   怀疑与"这一段压力对应袖带上沿的哪一段"有关，仍未查。
6. **`fresh_samples` 与 `[Capture] n` 差 6–8%** 的成因（整轮 vs 峰值后），需要在
   `tools/` 里写清楚哪个字段该用在哪，否则每份报告都要重新解释一次。
7. **`profile normal` 复位失败的长期影响**：今天 `already_peak` 只有 5/27 是好事，但 D8/D9
   那种"整天 already_peak"的日子意味着 profile 从来没被拨回 normal。协议层面应该明确写：
   `profile_already_peak=True` 是**允许路径**（只要 pre 零点在 ±5.0 内），不是缺陷。
8. **`rx_errors=204` 的来源**：拔插前后都是 204，不随拔插变化；D3 533、D4 772→876、
   D5 462→514、D6/D7 0、D8 0、D9 125、D10 204。它会跨天保留、只在 MCU 复位或长时间静默后
   跳变，机理仍未查。
9. **Windows 12:08:35 那次自动重启的触发原因**没有查（更新 / 崩溃 / 断电）。台架上跑长任务
   时这一条的风险最高，因为它是唯一一次把一整天作废的事件。建议查 `Event Viewer` 的
   `Kernel-General` / `Kernel-Power` 与 `WindowsUpdate` 日志（本会话非管理员，读不到全部）。
