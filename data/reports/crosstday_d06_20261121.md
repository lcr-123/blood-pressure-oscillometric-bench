## 2 开机锁存的 `SENSOR_INIT`：为什么采集脚本会否掉它

开机 `status`/`fault` 读到 `[Fault] code=3 name=SENSOR_INIT age=57034ms`，
同时 `[ADSdiag] stage=2 status=1 reg=0x01 err=0 state=0x20 sr1=0x0200 sr2=0x0000 errors=11 recoveries=11`。

固件来源（`blood pressure monitor/Core/Src/main.c`）：

```
1947  s_ads1115_ready = (ADS1115_Init(&hi2c1) == HAL_OK) ? 1U : 0U;
1949  if (s_ads1115_ready == 0U) {
1950      Debug_UART_Write("[Boot] ADS1115 offline; pressure command will retry\r\n");
1952      BP_Control_RecordFault(BP_FAULT_SENSOR_INIT);
1953  }
```

另一处运行时重试（`main.c:494-507`）也会打同一个码。`bp_control.c:44-51` 的
`BP_Control_RecordFault` **只写不清**；只有 `bp_control.c:68-79` 的 `BP_Control_Reset()`
会把 `s_fault` 置回 `BP_FAULT_NONE`。`BP_Control_Reset` 的调用点只有三处：
`main.c:699`（`ManualPump_Start` 内，`start` 命令必经）、`main.c:1583`（`deflate test` 起始，
仅当已在 `EMERGENCY`）、`main.c:1665`（`loaded pulse` 起始，同条件）。

**采集脚本的容忍逻辑只放行 `name=SENSOR_READ`**
（`tmp/bp_standard255_195_target275_peakwindow_20261105.py:260-264`：
`latched = any('name=SENSOR_READ' in s for s in fault)`，再要求
`recoveries >= 1 and healthy`）。`SENSOR_INIT` 不在白名单，会直接抛
`RuntimeError('initial sensor fault')`，整天第 1 轮就中止。D2 开工时那次
`code=4 name=SENSOR_READ` 能过，正是因为它在白名单里。

处置：`tmp/clear_fault_20261121.py` 走 `start` → 0.6 s → `stop` → `vent` → `seal`，
借 `ManualPump_Start` 内部的 `BP_Control_Reset()` 清掉。跑完 `code=1 name=USER_STOP`
（`stop` 的合法结果），之后全天每次 `fault` 都是 `code=0 name=NONE`、`errors=0 recoveries=0`。

副作用要写清：`start` 真的开了 0.6 s 泵，气路进了约 **+6.9 mmHg**；
`vent` 后 est 读数 6.10 一度不降，25 s 后基线才从 +6.87 收到 +2.59，
再经几次 30 s 观察稳在 +2.34…+2.42。**这 0.6 s 不是"空转"，它确实动了气路。**

| `standard120_080_target275_peakwindow_20261121-111959` | 1291 | 1 | 0 | `failed`（今天） |

→ **「单字节乱码杀整轮」在全库只有 2 例（11-13 与今天）**，间隔 8 天。
两例的形态完全一致：一个 U+FFFD 落在 `[Pressure]` 行首，`closeout_confirmed` 都是 `True`。

MCU 侧 `rx_errors` 全天为 0（28/28 `(0,0)`），所以这个字节是在
**MCU 的 UART 发送之后、桥接器的 UTF-8 解码之前**被弄坏的，不是 MCU 自己的错误计数能看到的。

### 3.3 为什么不建议在现场"容忍"它

严格说，单字符损坏并不必然意味着那 100 ms 的压力样本不可信。但这个守卫是
**11-05/11-06 那次事故之后加上的**（当时是 `sample failed` / `read failed` / `retry init`
这类真实故障），它把"线路出现不明字符"一律当作不可判定的证据。要放宽只能走 amend 流程，
而 amend 会按协议 §4 让本批次从改动日终止——**今天不动，留到批次结束后再议**。
代价是可算的：全库 623 轮里 2 轮，约 0.3%。

## 4 `profile normal` 复位失败：23/28 轮

### 4.1 现象与阈值

每轮结束时，采集脚本会尝试把 profile 从 `peak` 复位回 `normal`
（`tmp/bp_standard255_195_target275_peakwindow_20261105.py:381-396`，最多 3 次）。
今天 29 份元数据（28 轮 + 1 失败轮）里：

| 结果 | 轮数 | 收尾零点范围 |
|---|---|---|
| 复位成功（`profile_restored_readback` 非空） | **6** | **+0.069 … +0.721** |
| 复位失败（3 次全被拒，`[Profile] rejected: require inactive sealed fresh calibrated zero`） | **23** | **+0.923 … +2.529** |

两边**完全不重叠**，分界线在 +0.72 与 +0.92 之间。这与 §2 里 `profile peak` 的
`-1..+1` 是**同一个固件门**（`main.c:286-294` 检查最后一个压力样本），
只是复位时脚本不做"vent + 等稳定"那套准备，直接发命令，所以零点一旦高于 ≈+0.85 就必失败。

全天 `[Profile] rejected` 共 **69 行** = 23 轮 × 3 次，与上表一致。

### 4.2 与下一轮零点的耦合（同向，但不是逐轮一一对应）

复位失败意味着这一轮结束时 profile 停在 `peak`；下一轮开头
`profile_query_before_set` 会读到 `mode=peak`，于是**跳过 vent/seal/等稳定那一步**
（`:305-310` 的 `profile_already_peak` 分支），也就跳过了那次换气。
反过来，复位成功的那一轮之后，下一轮读到 `normal`，要真正做一遍
vent 3 s → seal → 等 40 个样本 ≤ +0.9，这一遍会带走残余气体。

块B 的零点序列正好卡在这个分界上：

| 段 | 轮数 | pre 均值 | 说明 |
|---|---|---|---|
| 块B 前 8 轮（B1–B4） | 8 | **+1.147** | 全部继承 `peak`，跳过换气 |
| 块B 后 6 轮（B5–B7） | 6 | **+0.250** | 从 `-124009` 起复位成功，每轮都换气 |

`-124009` 正是块B 第一轮复位成功的轮次（它的 post 零点 +0.069 低到能过门）。
这个自洽的循环可以解释"为什么块B 后半段零点突然整体下一个台阶"。

**但必须如实标注偏差**：`-122940`（块B P3 第 2 轮）pre 是 −0.132，
而它前面一轮 `-122549` 的 post 是 +1.666（复位失败）；`-123631`（P4 第 2 轮）pre −0.222，
前面 `-123314` 的 post 是 +1.378（也失败）。所以"复位失败 → 下一轮零点偏高"
不是逐轮必然，只是整体同向。**这条耦合关系是本日的推测，不是已证实的机理。**

### 4.3 对本批次判定的影响

**不影响**。每一轮开拍前都确认了 profile 是 `peak`（要么本来就 `peak` 跳过设置，
要么现场设置成功），28 轮全部 `export_received`。复位失败只是让"轮间 profile 状态"
与脚本作者的预期不同，记在元数据的 `profile_restore_error` 里，
判定器（`tmp/crosstday_analyse_20261116.py`）不读这个字段。

但这**会影响下一天的起始状态**：明天开工时 profile 很可能仍是 `peak`，
这意味着明天第一轮**不会**遇到 `-1..+1` 门（好事），但也意味着
"每轮都从 normal 现场设 peak"这个设定不再成立。**报告里必须写清楚，不能让后来人以为
28 轮都是现场设的 profile。**

## 9 还缺什么

1. **`SENSOR_INIT` 为什么会在开机时锁存**——`errors=11 recoveries=11` 说明 ADS1115 探测失败过
   11 次又自己恢复了，但固件只在开机那一刻记录一次故障。是不是 I2C 上电时序问题、
   还是 ADS1115 供电建立慢，未查。
2. **单字节乱码的来源**——MCU 侧 `rx_errors=0`，所以坏字节产生在 MCU 之后。
   是 FTDI 的帧错误、OmniProbe 的读取边界、还是 UTF-8 解码跨 chunk 切断多字节字符，
   三种都还没有证据区分。今天只出现 1 次，无法复现。
3. **`profile normal` 复位失败是否需要处理**——今天 23/28 轮失败，且让明天的起始 profile
   变成 `peak`。若明天仍然如此，"每轮现场设 peak"这个隐含前提就连续两天不成立，
   报告里必须逐日注明，不能让统计口径悄悄变。
4. **块B 零点在同一天内先高后低**——与 §4.2 的换气循环同向，但 `-122940`/`-123631`
   两个反例说明不是一一对应。是残气、还是"上一次换气后过了多久"的时间效应，未查。
5. **块A 内部 2.6 mmHg 的单向漂移**（−0.370 → +2.232，51.8 min）——比前几天的日间台阶大，
   但方向与 D5 的块B 上移相反。今天的漂移是"随时间上走"，D5 是"重缠后上走"，
   两者是不是同一机制，未查。
6. **P4 档的陡斜率离群**——D4、D5、D6 连续三天都出现在 P4，但今天块A 的 P4 不陡
   （−1.97 / −1.77）而块B 的两个都陡（−2.63 / −2.22），样本仍不足以定性。
7. **阀 flow 首次回落是真回落还是噪声**——0.33333 → 0.32042（−4.0%），两个分脉宽同向，
   若明天继续降则是拐点，若回到 0.33 则是单日抖动。
