# v3 验收测试：首批 10 轮（仅 Preset 4）

日期：2026-11-11
冻结记录：`data/protocols/reference_bp_freeze_v3.json`
结果文件：`data/reports/reference_bp_v3_validation_partial_p4.json`

## 结论先行

**这不是正式裁决。** 冻结记录要求"每预设 10 轮、共 40 轮"新采数据，目前只有
Preset 4 的 10 轮，占 1/4。按 `verdict_rule` 的定义，正式结论必须等另外三个预设的
30 轮采集完成。

在这 10 轮上，四条标准 **三条通过、一条不通过**：

| 标准 | 结果 | 实测 |
|---|---|---|
| MAP 发布数 ≥ 0.9 × v2 | **通过** | v3 9/10，v2 9/10 |
| MAP 误差 sd 比 v2 低 > 1.0 mmHg | **不通过** | 7.259 → 6.646，只低 **0.61** |
| MAP 中位 \|误差\| 不比 v2 差 1.0 以上 | **通过** | 2.74 → 2.96（+0.22） |
| \|误差\| > 20 的轮数不高于 v2 | **通过** | 0 → 0 |

如果把这批当作最终裁决，v3 应当被放弃、v2 继续作为冻结估算器。但只有 10 轮、
且只有最难的一档预设，现在还不到下这个判断的时候。

- 采集时段：2026-11-11 10:14–10:44，全部晚于冻结登记时刻 `2026-11-11T09:49:47`

## 为什么 sd 没有降够

v3 的动机是 `standard150_100_..._20261107-202606` 那类**单点尖峰**（v2 sd 12.01、
最差 86.93，v3 把它降到 sd 4.67、最差 16.34）。这批 P4 数据里没有那种尖峰：v2 最差
−18.38，sd 7.26 主要由两处构成——`104126` 的 −18.38（v3 拒绝发布，没进 sd 分母）
和 `102141` 的 +7.79。加宽窗口中位只能削平窄峰，削不动"峰位整体偏了 8 mmHg"这类误差，
所以 sd 只降 0.61。

`104126` 值得单独记一笔：v2 判 ok 给 −18.38，v3 判 `unresolved_sbp`（平台占比越过
0.25）。**v3 在这轮上做的事不是"更准"，而是"承认自己不知道"**，这符合两条标准里
"发布数不能崩"的通过条件，但也意味着它与 v2 的 sd 比较里少了一个大误差样本。

## 采集与打标过程中修掉的问题

冻结之后跑这批数据时，暴露出验收工具链的四个真实缺陷，全部已修：

1. **资格判据用的是文件路径**：`v3_acceptance.py` 把
   `data/raw/**/standard*_peakwindow_*.export.ndjson` 全算作已有语料，而新轮次也写进
   `development_20261101`，于是**第一次真正的验收批被自己的脚本判成"全部已评分"**。
   改为按 run_id 里的采集时刻与 `REGISTERED_AT = '2026-11-11T09:49:47'` 比较。
2. **预设解析错位**：run_id 是 `standard255_195_...`，首段是 `standard255` 而不是
   `standard`，原实现按 `_` 切三段取 `head[1:3]`，永远返回 None。
3. **无参考时把判据当 FAIL**：`--panel-map` 缺条目时 sd/中位/离群三条算不出来，
   原代码把"算不出"渲染成 FAIL，看起来像真的裁决。现在区分
   `n/a` 与 `FAIL`，并在这种情况下给出 `NOT EVALUABLE`。
4. **元数据与代码门限不一致**：`closeout_criterion` 字符串写死 0.8 mmHg，而
   `closeout_sealed_zero(..., sealed_ceiling=1.2)` 实际比的是 1.2。字符串改为由同一
   变量拼出，并补 `closeout_criterion_note`。

另外新增 `tools/panel_map.py`：从每轮自己的 metadata 生成 `run_id → panel_map_mmhg`
表，避免手工抄写面板值——抄错一个数就会静默改掉整张误差表。
