### 2.2 错误码定论

`tmp/d9_adstime_20261124.py` 扫今天全部 `d9_*.ndjson` 的 44 条 diag 事件，错误码只有两种：

| 码 | 宏 | 抛出点 | 含义 |
|---|---|---|---|
| `0x00000200` | `HAL_I2C_WRONG_START` | `stm32f1xx_hal_i2c.c:3577` | **START 条件请求了但 SB 没置起**，返回 `HAL_TIMEOUT` |
| `0x00000020` | `HAL_I2C_ERROR_TIMEOUT` | 同上头文件 `:169` | 总线超时 |

原文（`blood pressure monitor/Drivers/STM32F1xx_HAL_Driver/Src/stm32f1xx_hal_i2c.c:3577`）：

```c
if (READ_BIT(hi2c->Instance->CR1, I2C_CR1_START) == I2C_CR1_START)
{
  hi2c->ErrorCode = HAL_I2C_WRONG_START;
}
return HAL_TIMEOUT;
```

**两者都不是 AF/NACK**——从机没有拒绝地址，是**主机侧连 START 都没能发出去**（或没等到 SB）。
这与此前把 `0x200` 读成 "AF 应答失败" 的判读不同，今天的证据（`scl=0 sda=0` 会随后恢复、
`[ADSbus] cr1=0x0501`）指向总线被拉低 / 上拉不足 / 接触电阻，而不是器件 NACK。

`errors` 的爬升（`tmp/d9_adstime_20261124.py`）：

| 时刻 | errors | recoveries | 场景 |
|---|---|---|---|
| 11:02:02 | 4 | 4 | 开机即带 4 次（昨夜留下的计数） |
| 11:04:33 | 5 | 4 | vent watch 第一次读失败（`err=0x00000004` = AF） |
| 11:05:35 | 10 | 9 | seal watch |
| 11:06:02 | 11 | 11 | `d9_sealed` |
| 11:24:47–11:25:01 | 12 → **18** | 11 → 17 | **爆发段：连续 7 次失败 + retry init** |
| 11:26:36 | 18 | 18 | 爆发结束 |
| 11:27:05 | 20 | 19 | `stage=3 err=0x00000020`（TIMEOUT） |
| 11:32:13 | **0** | **0** | **归零** |

爆发段里有一次 `[ADS1115] Init OK address=0x48 config=0x8583`（正常是 `0xC383`）。
`0x8583` 与 `0xC383` 只差 `0x4000`（`ADS1115_MUX_AIN0_GND`），而
`ads1115.c:106` 的 `ADS1115_Init` 里那一行是 **读回** 配置寄存器：

```c
status = ADS1115_ReadRegister16(ADS1115_REG_CONFIG, &config);
...
s_config = config;
```

所以 `0x8583` 不是"写错了配置"，而是**读回的那一刻器件正处于单次转换的中途**
（MUX 位随转换状态变化），本身就是总线不稳的旁证。

### 2.3 固件为什么把坏读数当正常值

三个环节串起来，坏样本一路无阻：

1. `ads1115.c:154-158` `ADS1115_ReadRaw`：`*raw_value = (int16_t)conversion;` ——
   只要 HAL 传输成功就返回 `HAL_OK`，**`conversion == 0x0000` 不判错**；
2. `ads1115.c:215-218`：`if (next.pressure_mmhg < 0.0f) { next.pressure_mmhg = 0.0f; }` ——
   零点附近负压被钳成 0（所以 `est` 永远 ≥0，读不出来"掉到零以下"）；
3. `main.c:461`：`BP_Control_IsCalibrationValid() ? "VALID" : "UNCAL"` ——
   日志里的 `VALID` 说的是**校准记录有效**，不是"这一帧有效"。

这与 D7 §2 的 `raw=0` 坏样本是同一个机理的两种表现：D7 那次是**一帧全零**（触发
`raw<1000` 守卫），今天这次是**连续多帧漂移**（数值都在 1000–3000 之间，守卫抓不到）。

### 2.4 恢复路径与「只能是 MCU 重启」的推断

`ads1115.c:43-55` 的 `ADS1115_I2C_Recover()` 只做
`recovery_count++` → `HAL_I2C_DeInit` → `__HAL_RCC_I2C1_FORCE_RESET()` →
`RELEASE_RESET` → `HAL_I2C_Init`，注释里自己写明：

> No GPIO clock pulsing; this cannot repair a slave physically holding the bus low

而 `errors` / `recoveries` 是 `ads1115.c:15` 的
`static ADS1115_Diagnostics_t s_diag = {0};`，**只能靠 MCU 重启归零**
（`:36` / `:47` 两处只增不减）；锁存的 fault 也只有 `bp_control.c:68-79`
的 `BP_Control_Reset()` 能清（`bp_control.c:44-51` 只写不清）。

11:32:12 那一次同时满足三件事：

- fault 从 `code=4 SENSOR_READ` → `code=0 NONE`；
- `[ADSdiag]` 从 `errors=20 recoveries=19` → **`0/0`**；
- 基线从 `sensor 306–308 mV`（true +5.30…+5.47）跳到 `225–227 mV`（true −1.28）。

→ **只能是 MCU 重启**。但 11:26:43–11:31:03 之间的窗口没有客户端持有 socket，
`[Boot] reset_csr=…` 横幅没被任何人读到；`tmp/scan_resets_20261123.py` 重扫全库
**2077 份 ndjson，reset 横幅仍只有 4 条、全是 `0x04000000` 纯 PIN**
（11-09 `dataset_step240b`、11-10 `sag_test`、11-21 `d6_state3`、11-23 `daily_leak`），

**所以今天这次重启没有任何寄存器证据**，只有间接指纹。这与 D8 §5 那四例的区别是：
D8 的四例是**横幅被抓到、但没人在观测时预期它会来**；今天这次是**观测窗口之间发生的、没人听**。

### 3.3 与 D8 的对照：自设门是更大的坑

D8 §3 已经踩过一次「自己写 `LO, HI = -0.6, 0.6` 把门收紧、
结果把本来能过的 +0.86 挡住」。今天这次是相对的第二种情形：
**门是对的（±1.0），但被测量骗了**。两次都说明同一件事——
`set_peak_profile` 这类脚本必须

   ③给 `ADS1115_I2C_Recover()` 加真正的 GPIO 时钟脉冲（9 个 SCL 脉冲 + STOP）。

   fault 清零 + 基线跳变）指向重启，但 `[Boot] reset_csr=…` 无记录。
