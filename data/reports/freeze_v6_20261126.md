# 冻结 v6（2026-11-26）：把压力轴钉进记录，并让基线可以被重算

**本文件记录一次冻结声明。它不产生任何 MAP / SBP / DBP 估计值，也不改变已发布的 62 轮语料。**

---

## 0 一句话

前四份冻结记录（v1 / v2 / v3，以及从未成为 JSON 的 v5 候选）钉的是**代码哈希与常量**，
不钉**压力轴**。轴是固件在采集时烧进每份导出 `p` 值里的，所以 2026-11-26 重标定之后
`tools/verify_freeze.py` 仍然报「三份完好」，而这三份记录各自写的基线数字**已经不可能由
当前硬件产生**——它们只在那条旧轴上成立，而记录里没有一个字说明这一点。v6 补上两样东西：
`pressure_axis`（斜率、截距、以及基线轮次实际是在哪条轴上采的）与 `recompute_method`
（重算工具及其哈希），并让 `verify_freeze.py` **对 v6 重跑基线、比对字节**，而不只是比哈希。

---

## 1 这个缺陷是怎么暴露的

### 1.1 三份旧记录只钉了代码

`tools/verify_freeze.py` 原来 140 行，只做三件事：比对 `estimator.sha256`、比对
`baseline_report_sha256`、比对 `validity_gate.sha256`，然后把各模块的常量 `repr()` 与记录里的
字符串逐项对比。**它从不重跑基线，也从不读压力轴。**

| 记录 | 文件 | estimator | baseline report | gate | 钉压力轴 |
|---|---|---|---|---|---|
| v1 | `data/protocols/reference_bp_freeze_v1.json`（8279 B） | `tools/reference_bp.py` `ddc9daf7…` | `data/reports/reference_bp_20261107.json` `a50a905b…` | 无 | **否** |
| v2 | `reference_bp_freeze_v2.json`（9729 B） | 同上 | 同上 | `tools/validity_v2.py` `0857b93a…` + 6 常量 | **否** |
| v3 | `reference_bp_freeze_v3.json`（5765 B） | `tools/reference_bp_v3.py` `0007c474…` | `data/reports/reference_bp_v3_baseline_20261111.json` `0d74bbbb…` | 同上 | **否** |
| v5 | **只有** `reference_bp_freeze_v5_candidate.md` | 未钉 | 未钉 | 未钉 | **否** |

v3 的 `relationship_to_v2` 自己写得很清楚它是个 wrapper：「it imports tools/reference_bp.py and
overrides exactly one default (DEFAULT_MAP_SMOOTHING_S 2.0 -> 3.0)」。v5 的情况更弱：那份预注册
md 里**一个 sha256 字面量都没有**（`re.findall(r'[0-9a-f]{64}')` 返回 0 条），所以
`tools/covered_bp.py` 的九个常量从来没被任何机器可校验的东西钉住过。

### 1.2 换轴之后，数字对不上了

v2 记录里写的是 `baseline_summary` = 18 轮 / 16 ok / `map 3.7 / sbp 9.7 / dbp 9.6`
（population sd；记录同时附了 `sample_sd` 3.82 / 10.0 / 9.92）。在 18 轮 `frozen_baseline_v2`
上重算：

| 轴 | MAP mean/sd | SBP mean/sd | DBP mean/sd | 复现记录 |
|---|---|---|---|---|
| 旧轴 82.326 / −19.887（采集时） | +4.463 / **3.703** | −0.229 / **9.684** | +0.863 / **9.603** | **是** |
| 新轴 81.5286 / −20.0279（今天） | +2.789 / **3.819** | −2.167 / **9.770** | −0.625 / **9.416** | **否** |

也就是说：**记录没有错，它写的是当时的事实；错的是它没写清楚那个事实依赖哪条轴。**
一个不能被重算的基线，等于一个不能被检验的基线。

### 1.3 为什么工具不会自己报警

- 645 份导出的 `begin` 行记录的标定**全是旧轴**：`slope=82.3260 intercept=-19.8870 n=645`，
  没有任何一份写新轴。历史导出永远按旧轴解释，改固件标定不会改写历史。
- `tools/` 里 grep `slope|intercept` 共 107 处，**没有一处读导出 `begin` 的 slope**。
  `tools/corpus_register.py` 里那个 `slope` 是 `validity_v2.check()` 的峰窗斜率
  （`peak_window_slope_mmhg_s`），不是压力轴斜率。
- 于是轴变了，工具全部沉默。这正是这个缺陷能一直藏着的原因。

## 2 v6 加了什么

### 2.1 `pressure_axis`

```json
"pressure_axis": {
  "name": "refit_20261126",
  "slope": 81.5286,
  "intercept": -20.0279,
  "capture_slope": 82.326,
  "capture_intercept": -19.887,
  "source_commit": "c60ef1f",
  "derivation": "p_new = (1 + b) * p_old + a with a = -0.3368, b = -0.009686 …"
}
```

`capture_slope` / `capture_intercept` 这一对是重点：它记录**基线轮次实际是在哪条轴上采的**。
没有它，读者无法判断记录里的数字来自哪条轴——那正是 v1/v2/v3 的毛病。

同时写进记录的还有 `calibration_write`（命令、读回、以及**为什么必须先 `cal clear`**）与
`rollback`（`cal clear; cal write 82.326 -19.887`）。

### 2.2 `covered_estimator`

`tools/covered_bp.py`（18285 B，`37e088ee…`）连同九个常量被正式钉进 JSON：

| 常量 | 值 |
|---|---|
| `FS_HZ` | 40.0 |
| `BAND_HZ` | (1.0, 2.0) |
| `SMOOTH_S` | 2.0 |
| `MIN_VIEWS` | 2 |
| `PULSE_PRESSURE_FRACTION` | 0.15 |
| `NOTE_GAP_MMHG` | 10.0 |
| `MAP_OFFSET_MMHG` | −5.31 |
| `DBP_OFFSET_MMHG` | −1.16 |
| `SBP_OFFSET_MMHG` | 0.0 |

记录里 `status` 字段明写：**它是候选，不是已验证的估算器**。它自己的预注册验收
（`data/reports/v5_validation_20261114.md`，71 轮）C1 / C2 / C4 / C5 全 FAIL，所以已发布的
参考算法输出**仍然是冻结 v2**，三视图中位只能作为并列候选报，且必须带上它的失败项。
钉它进来只是让「有人偷偷改了常量」这件事变成可检测，不是给它背书。

### 2.3 `recompute_method` 与 `tools/freeze_baseline.py`

新工具 `tools/freeze_baseline.py`（`6ffde1a1…`）做一件事：**在记录钉的那条轴上，从那一组轮次
把基线重算一遍**，同时给出 population sd（n）与 sample sd（n−1）两种口径——因为旧记录把
population sd 放在 `baseline_summary`、把 sample sd 放在 `baseline_summary.sample_sd`，
比对时不该取决于读者以为的是哪一个。

当钉的轴与采集轴不同，它还额外输出一份**采集轴读数**，让两者无法被混为一谈。

**确定性**：输出是 (tier, 轴, 采集轴, 轮次集合) 的纯函数，没有路径、没有标签、没有时间戳。
同输入两次运行字节完全相同——已实测：

```
WROTE data\reports\v6_baseline_20261126.json  6038 bytes  sha256 96ec6a948afa36c2…
WROTE tmp\omniprobe\v6_baseline_rerun.json    6038 bytes  sha256 96ec6a948afa36c2…
```

这正是能让记录 hash 自己基线报告、并让别人复算那个 hash 的前提。

### 2.4 `verify_freeze.py` 现在会重跑基线

对**声明了** `pressure_axis` + `recompute_method` 的记录（目前只有 v6），它执行：

```
python tools/freeze_baseline.py --axis-slope <record> --axis-intercept <record> \
    --capture-slope <record> --capture-intercept <record> --tier <record> --out <tmp>
```

然后把结果文件的 sha256 与 `baseline_report_sha256` 比对。工具本身也按 `recompute_method.sha256`
校验。**只声明一半机制（有轴没方法，或反过来）会被判为 FAIL**——否则把 `pressure_axis` 一删，
基线就悄悄不检查了。

**对 v1/v2/v3 故意不重跑基线**：它们既没钉轴也没钉方法，其数字只在采集轴上成立而记录不说明；
给旧记录临时引入新的失败模式，等于追溯性地把一个已发表的 holdout 弄坏。它们现在会打印一条
说明（`--  this record pins no pressure axis …`），但不判失败。

## 4 v6 的基线数字（同记录三条）

18 轮 `frozen_baseline_v2`，gate 拒绝 0，发布 16。两条轴并列，**只有 pinned 那一条是 v6 的主张**：

| 轴 | 口径 | MAP | SBP | DBP |
|---|---|---|---|---|
| 81.5286 / −20.0279（pinned） | population sd | +2.789 / **3.819** | −2.167 / **9.770** | −0.625 / **9.416** |
| | sample sd | — / 3.944 | — / 10.090 | — / 9.725 |
| | max abs | 8.71 | **22.39** | 21.14 |
| 82.326 / −19.887（capture） | population sd | +4.463 / **3.703** | −0.229 / **9.684** | +0.863 / **9.603** |
| | sample sd | — / 3.824 | — / 10.001 | — / 9.918 |
| | max abs | 10.76 | 20.31 | 23.15 |

两点必须一起读：

1. **这 18 轮是描述性统计，不是精度主张**——它们被用来挑估算器，所以永远不能验证它。
2. **新轴上 SBP 的 max abs 从 20.31 涨到 22.39**。这不是新错误，是原来被旧轴那 −0.23 的系统
   偏差压住的尾部露出来了。同一件事在跨天 265 轮上更明显：静默 >20 的轮次从 20 涨到 26
   （见 `data/reports/pressure_axis_rebook_20261126.md` §6）。**换尺子会暴露被偏差掩盖的错误，
   看起来像变坏，其实是变真。**

## 5 v6 不做什么

- **不重判历史。** 645 份导出是在 82.326 / −19.887 上采的，引用它们的任何数字都必须标明轴。
  已发布 62 轮保持它被评分时的数字（frozen v2、采集轴）；在收数轴上重算是另一件明确标注的
  练习，不把任何一轮移进或移出已发布集合。
- **不验证 `covered_bp`。** 它 C1/C2/C4/C5 全 FAIL，仍是候选。钉住它只是为了防篡改。
- **不解决供电轨漂移。** 轴被钉成一对数字，不是一个测量协议；2026-11-10 那次供电轨在 15 分钟
  内从 5.133 漂到 5.149 V（0.31 %），而 1.7 % 的斜率差足以推翻这次重标定。
- **不填 268–275 mmHg。** 那段仍是外推，受 `blood pressure monitor/Core/Inc/bp_control.h:29`
  的 `BP_MAX_PRESSURE_MMHG 280U` 限制。
- **不测温度、迟滞、长期稳定性。** 三者仍为未测项。

## 6 保留下来的已知缺陷

**`blood pressure monitor/Core/Src/bp_cal.c:137`**：`BP_Cal_Write()` 只调 `BP_Cal_FlashProgram()`，
从不调 `BP_Cal_FlashErasePage()`（擦除只在 `:158` 的 `BP_Cal_Clear()` 里）。Flash 只能把 1 写成 0，
所以**用不同值覆盖已有记录必定失败，且旧记录静默保留**。2026-11-26 重标定时第一次
`cal write 81.529 -20.03` 就是这样失败的（`[Cal] write FAILED (bad values or flash error)`），
绕法是先 `cal clear`。这是固件 bug，不是操作失误，已列入工程债。

**`tools/covered_bp.py` 的体现方式仍然分裂**：文件哈希现在钉在 v6 里了，但九个偏移常量是在
旧轴上拟合的（`MAP_OFFSET_MMHG −5.31`、`DBP_OFFSET_MMHG −1.16` 来自 `frozen_baseline_v2`
14 轮）。重算账本时跑过三组变体（保持原值 / 机械平移 `offset − C` / 新轴重拟），
**三组都是 5/7、失败档集合相同（P2 与 P4 的 SBP），只挪 pooled 均值 0.3–0.7 mmHg**
（`pressure_axis_rebook_20261126.md` §5）。所以 v6 **不改**这些常量——改了就等于破掉
v5 候选预注册，收益为零。这件事留给下一个走完整预注册的版本。

## 7 复现

```bash
python tools/verify_freeze.py
python tools/verify_freeze.py --list
python tools/verify_freeze.py --name reference_bp_v6

# 重算基线，sha256 必须等于记录里的 baseline_report_sha256
python tools/freeze_baseline.py --record data/protocols/reference_bp_freeze_v6.json \
    --out /tmp/v6_baseline.json

# 只看记录钉的轴
python tools/freeze_baseline.py --record data/protocols/reference_bp_freeze_v6.json \
    --print-record-axis

# 反向测试：证明检查器不是摆设
python -X utf8 tmp/verify_negative_20261126.py
```
